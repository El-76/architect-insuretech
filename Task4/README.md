### osago-aggregator

#### Общее описание

Читает из Kafka команды от core-app вида "обработать заявку с такими-то параметрами", команда содержит UUID заявки, который генерируется клиентом, и её характеристики.

Прочитал команду, отправил N команд в Kafka вида "создать заявку у поставщика X с такими-то параметрами" - по одной на каждого поставщика, commit offset.

Также читает команды "создать заявку у поставщика X с такими-то параметрами", на каждую делает запрос "создать заявку на ОСАГО" в соответствующего поставщика, получает ID заявки у поставщика, отправляет команду в Kafka "получить предложение по заявке с идентификатором ID у поставщика X", commit offset.

Также читает команды "получить предложение по заявке с идентификатором ID у поставщика X", на каждую делает запрос "получить предложение по заявке" в соответствующего поставщика (скорее всего не сразу, а с некоторой сконфигурированной заранее паузой для конкретного поставщика, иначе схема заявка-предложение в двух разных запроса не имела бы смысла), записывает ответ (предложение) в Kafka, commit offset.

#### Мотивация решения

Была рассмотрена альтернатива с очередями поверх БД, но нагрузка на запись в 2500 rps помноженные на количество поставщиков уже выглядит как потенциально требующая масштабирования БД, что выглядит сложнее, чем Kafka.

Транзакций нет, поэтому запросы в поставщиков могут дублироваться при падении сервиса, но это не выглядит проблемой тк это просто получение предложений. Если это всё-таки проблема, можно использовать Kafka Transactions для атомарных commit offset + send.

#### Детали реализации

Для изоляции проблем с одним поставщиком от других используется паттерн **Bulkhead**.

Запросы в поставщиков делаются thread pool, он свой для каждого поставщика, чтобы thread pool работал корректно нужно реализовать логику commit offset так, чтобы она всегда делала коммит только обработанным командам (если например обработаны команды 1 и 3, а 2 - ещё нет, то commit можно делать только команде 1).

Команды, относящиеся к конкретному поставщику попадают в отдельный топик (партиций недостаточно, тк никто не гарантирует, что в одну партицию не попадут команды двух разных поставщиков).

Чтобы уменьшить проблемы с неработающим поставщиком, можно использовать комбинацию паттернов во время запроса к ним:

* **Rate Limiter** - дабы не превышать проектную нагрузку
* **Circuit Breaker** - чтобе не DDOS-ить зря поставщиков
* **Timeout** - при превышении времени обслуживания запросв, чтобы thread pool не "залип"
* **Retry** - для повторения неудачных запросов, но пытаемся не дольше чем 60 сек суммерно как и сказано в требованиях

Таким образом:

* Уложимся в SLA по нагрузке на поставщиков
* Нивелируем эффекты от поломанного поставщика на всю систему
* Будет своего рода graceful degradation - если один поставщик деградирует, предложения от остальных продолжат поступать

### Взаимодействие и логика клиента, web-приложения и core-app

#### Общее описание

Клиент генерирует UUID и отправляет запрос на расчёт в web-приложение по HTTP - SSE, ждёт.

web-приложение пользуется единственной REST-like ручкой core-app, которая тоже использует SSE:

```
POST /v1/application
```

В body - UUID заявки (генерируется клиентом),  характеристики заявки.

core-app отправляет команду "обработать заявку с такими-то параметрами" для osago-aggregator в Kafka, создаёт пустое состояние (map) заявки в Redis с ключом UUID заявки и некотороым TTL (длина "сессии" пользователя при покупке страховки).

При получении сообщения с предложением core-app обновляет состояние заявки в Redis (добавляет предложение в map с ключом provider_id), отдаёт обновление состояния по SSE web-приложению, web-приложение - клиенту.

Если пользователь нажмёт Refresh или соединение разорвётся и клиент повторит запрос в Redis будет актуальное состояние заявки.

### Остальное

Остальной flow предполагается что сделан на существующих "рельсах" - как только параметры предложения известны - создаём пользовательскую заявку и тп как и ранее.

### Явные ответы на вопросы из задания

1. Проработайте реализацию osago-aggregator - см. выше   Решите:
2. Требуется ли ему своё хранилище данных? - да, тк система должна переживать рестарт, но роль хранилища играет Kafka (см. раздел мотивация решения)
3. Какой API он предоставляет core-app? - "обработать заявку с такими-то параметрами" на входе, сообщение "предложение поставщика" на выходе 
4. Определите средство интеграции между сервисами core-app и osago-aggregator - Kafka
5. Подумайте над API для веб-приложения в core-app - REST-like ручка - см. выше
6. Определите средство интеграции между веб-приложением и core-app. Если будете использовать средство, отличное от REST, отразите интеграцию новой стрелкой - HTTP / SSE
7. В зависимости от выбранных средств интеграции подумайте, требуется ли где-то применение паттернов отказоустойчивости: Rate Limiting, Circuit Breaker, Retry , Timeout - при взаимодействии с поставщиками, см. описание. Отобразите применение паттернов на схеме с помощью обозначений из этой библиотеки - готово  
8. Примите во внимание, что сервисы задеплоены в нескольких экземплярах. Подумайте, зависит ли ваше решение от этого - да, зависит, например запрос от web-приложения может попасть в один экземпляр core-app, а сообщение с предложением обработано другим экземпляром - для этого сделан Redis, также Kafka хранит состояние при обращении к поставщикам, благодаря этому osago-aggregator тоже может быть запущен в нескольких экземплярах.
