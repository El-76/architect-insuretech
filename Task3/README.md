## As Is

### Проблемы и риски

* Отказоустойчивость - ручка получения доступных продуктов агрегирует данные из всех поставщиков и, таким образом, уязвима к сбоям в любом из них
* Отказоустойчивость - при добавлении поставщиков надёжность ручки получения продуктов будет падать
* Масштабируемость - при получении доступных продуктов не учитываются особенности каждого поставщика - может быть так, что обновление раз в 15 минут для каких-то поставщиков бессмысленно
* Горизонтальное масштабирование затруднено - у ручки получения продуктов сейчас минимум два клиента - какие-то вызовы получаются лишние, также как-то надо решать проблему повторных вызовов разными экземплярами одного сервиса, проблема многих экземпляров также актуальна и для ручки получения оформленных страховок
* Отказоустойчивость - схема с периодическим опросом core-app для получения оформленных страховок выглядит ненадёжной и она не продиктована никаким внешним API, также возможно можно как-то будет использовать факт, что при асинхронном взаимодействии можно обрабатывать данные по страховкам и формировать данные сверки в реальном времени (хотя это вряд ли понадобится) 

## To Be

### Обновление продуктов и тарифов

ins-product-aggregator получает информацию по продуктам и тарифам из разных поставщиков раз в 15 минут (или раз в период, специфичный для каждого поставщика) и публикует её в Kafka, топик product-info.

Если один поставщик что-то не вернул можно сделать несколько retry, при неудаче дождаться следующего обновления.

Поломка одного поставщика не останавливает процесс обновления и рассылку событий - поставщики независимы.

Transactional Outbox тут не нужен - нет обновляемых бизнес-сущностей.

Вопрос в формате сообщений - стоит рассмотреть вариант, когда все продукты одного поставщика живут в одном сообщении - тогда не надо будет хранить состояние текущих продуктов и посылать сообщение "продукт удалён" и тп. Тк продуктов и тарифов не очень много, такой подход выглядит достижимым.

core-app и ins-comp-settlement обновляют свои реплики по событиям выше.

### Обновление оформленных страховок

core-app публикует события по страховкам в Kafka, топик orders.

Здесь используется Transactional Outbox - в одной транзакции создаётся или обновляется страховка и создаётся запись в таблице сообщений в очереди.

ins-comp-settlement обновляет свою реплику по событиям выше.

Сервис ins-comp-settlement отмечает в своей реплике, какие страховки уже переданы для взаиморасчётов. Если есть требование "отрезать" оформленные страховки строго по календарному дню, то core-app может отсылать событие "закрытие дня" в те же партиции, что и страховки - так ins-comp-settlement поймёт, что сегодня больше страховок не будет (иначе есть риск при сбоях или перегрузке не дочитать страховки за текущий день).
